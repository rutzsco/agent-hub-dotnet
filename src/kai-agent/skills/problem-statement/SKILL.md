# Problem Statement Guidance

Help users write clear, data-driven problem statements. A strong problem
statement is the foundation of any successful improvement event.

## Structure of a Good Problem Statement

A quality problem statement answers **What, Where, When, How Much** without
stating **Why** (that comes during root cause analysis):

> **[What]** is happening **[Where]** — the current performance is **[How Much]**
> against a target/standard of **[Target]**, resulting in **[Impact]**.

## Step-by-Step Guide

### Step 1: Identify the Gap
- What is the current performance level? (Use data, not opinions)
- What is the expected or target performance?
- What is the gap between current and target?

### Step 2: Quantify the Impact
- What is the business impact of this gap? (Cost, time, quality, safety, customer satisfaction)
- How is this gap trending? (Getting worse, stable, seasonal?)
- How long has this gap existed?

### Step 3: Define the Boundaries
- Where exactly does this problem occur? (Location, process, product, shift)
- When does it occur? (Always, sometimes, specific conditions?)
- Who is affected? (Customers, operators, downstream processes)

### Step 4: Check for Anti-Patterns
Ensure the problem statement does NOT:
- ❌ Include a solution ("We need to buy new equipment")
- ❌ Assign blame ("Operators are not following procedures")
- ❌ Use vague language ("Quality is bad", "Things are slow")
- ❌ Include the root cause ("Because our software is outdated")
- ❌ Cover multiple unrelated problems

## Quality Checklist
- [ ] Contains at least one quantified metric
- [ ] Describes current state vs. target state
- [ ] Specifies where the problem occurs
- [ ] Quantifies business impact
- [ ] Free of assumed solutions
- [ ] Free of blame or root cause assumptions
- [ ] Specific enough to be actionable in one event
